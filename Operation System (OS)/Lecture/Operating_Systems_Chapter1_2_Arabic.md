# Chapter 1 — Introduction

## 1. يعني إيه Operating System أصلًا؟

تخيّل إنك فتحت برنامج على اللابتوب، وعايزه يقرأ ملف من الـ SSD، ويعرض البيانات على الشاشة، وفي نفس الوقت فيه متصفح شغال وبيستخدم الإنترنت.

كل برنامج من دول محتاج موارد من الجهاز: **CPU**، **Memory**، **Storage**، و**I/O devices**. مين ينظّم استخدام الموارد دي؟ ومين يمنع برنامج إنه يبوّظ شغل برنامج تاني؟ هنا بييجي دور **الـ Operating System (OS)**.

الكتاب بيعرّف الـ OS بأنه:

> **A program that acts as an intermediary between a user of a computer and the computer hardware.**

يعني هو **وسيط** بين المستخدم والـ Hardware، بدل ما كل برنامج يتعامل مع مكونات الجهاز بشكل مباشر ومن غير تنظيم.

### المكونات الأربعة للنظام (The four components of a computer system)

| المكوّن | الوصف |
|---|---|
| **Users** | المستخدمون: الأشخاص، الآلات، حواسيب أخرى |
| **Application Programs** | برامج تطبيقية: Word processors, compilers, browsers, databases, games |
| **Operating System** | يدير الموارد ويتحكم في التنفيذ |
| **Hardware** | المكونات المادية: CPU, main memory, I/O devices |

⚠️ خلّي بالك من الفرق:

- **Hardware**: المكونات الفعلية، زي المعالج والرام والهارد.
- **Operating System**: ينظّم ويتيح استخدام المكونات دي.
- **Application Programs**: البرامج اللي بتحل مشاكل المستخدم باستخدام الموارد المتاحة.

> 💡 مثلًا، الـ **compiler** برنامج تطبيقي؛ بيترجم الكود. لكن لما يحتاج يقرأ ملف أو يكتب ناتجًا، بيستخدم خدمات النظام المناسبة بدل ما يدير الـ Hardware كله بنفسه.

### أهداف نظام التشغيل (Operating System Goals)

الملف محدد 3 أهداف أساسية:

1. **Execute user programs**: تشغيل برامج المستخدم ومساعدته على حل مشكلته.
2. **Convenience**: جعل استخدام الجهاز أسهل وأكثر راحة.
3. **Efficiency**: استخدام الـ Hardware بكفاءة.

وفيه منظوران مهمان لفهم وظيفة النظام:

- **من منظور المستخدم (User view):** المستخدم عايز الجهاز يكون سهل وسريع ويستجيب كويس، ومش بالضرورة يهتم المعالج قضى وقته إزاي.
- **من منظور النظام (System view):** الـ OS هو **Resource Allocator** و**Control Program**:
  - **Resource Allocator:** بيوزّع الموارد بين البرامج والمستخدمين، وبيحل التعارض بين طلباتهم بطريقة فعّالة وعادلة.
  - **Control Program:** بيتحكم في تنفيذ البرامج لمنع الأخطاء والاستخدام غير السليم للجهاز.

> 💡 مثال: لو برنامجين عايزين يستخدموا الـ CPU، النظام يحدد مين يشتغل وإمتى. ولو برنامج حاول ينفّذ عملية ممنوعة، النظام لازم يقدر يحدّ من التصرف ده.

### OS vs Kernel vs System Programs

مفيش تعريف عالمي واحد متفق عليه لكل ما يدخل تحت اسم Operating System؛ لأن الشركات بتختلف في المكونات اللي بتضمّنها مع النظام. لكن في مصطلح أساسي لازم تعرفه:

- **Kernel:** الجزء الأساسي من النظام، واللي بيظل شغّالًا كجزء محوري من إدارة الجهاز. الكتاب بيصفه بأنه **البرنامج الذي يعمل طوال الوقت على الكمبيوتر**.

أما باقي البرامج فممكن تكون:

- **System Programs:** برامج مساعدة بتيجي مع النظام.
- **Application Programs:** برامج هدفها تنفيذ احتياجات المستخدم.

> ✅ إذًا، **مش كل برنامج تابع للنظام هو الـ Kernel نفسه**. دي نقطة مفاهيمية مهمة.

## 2. Computer Startup — الجهاز بيبدأ تشغيله إزاي؟

لما تدوس Power، الـ OS مش بيكون بدأ شغله بالفعل من أول لحظة؛ فيه خطوات تسبقه.

الملف بيسمّي أول برنامج **Bootstrap Program**، وهو بيبدأ عند تشغيل الجهاز أو إعادة تشغيله، وغالبًا بيكون محفوظًا في ذاكرة ثابتة مثل **ROM** أو **EPROM**، ضمن ما يُعرف باسم **Firmware**.

**الوظائف الأساسية للـ Bootstrap Program:**

1. تهيئة مكونات الجهاز (Initialize system components).
2. تحميل الـ OS Kernel إلى الذاكرة.
3. بدء تنفيذ الـ Kernel.

```text
Power on / Reboot
    │
    ▼
Bootstrap Program — Firmware
    │
    ▼
Initialize hardware and load kernel
    │
    ▼
Kernel starts executing
```

> ⚠️ **الـ Firmware والـ Kernel مش نفس الحاجة.** الـ Firmware يساعد في بدء التشغيل، والـ Kernel هو الجزء الأساسي من نظام التشغيل الذي يتم تحميله ليبدأ إدارة الجهاز.

## 3. Computer-System Organization — الـ CPU والأجهزة بيتعاملوا إزاي؟

الكتاب بينتقل من تعريف الـ OS إلى طريقة تنظيم الجهاز نفسه.

الـ Computer System ممكن يحتوي على CPU واحد أو أكثر، بالإضافة إلى **Device Controllers**، وكلهم متصلون عبر **Common Bus** يتيح الوصول إلى الذاكرة المشتركة.

### المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| **CPU** | ينفّذ التعليمات |
| **Main Memory** | تحتفظ بالتعليمات والبيانات التي يحتاجها التنفيذ |
| **Device Controller** | مسؤول عن نوع معين من أجهزة الإدخال والإخراج |
| **Local Buffer** | مساحة مؤقتة لدى الـ Controller لتجميع البيانات أو الاحتفاظ بها أثناء عملية الـ I/O |
| **System Bus** | وسيلة الاتصال المشتركة بين المكونات |

### مثال: قراءة ملف من الـ SSD

بدل ما تتخيّل أن المعالج بيقرأ كل بايت بنفسه مباشرة من الجهاز، فكّر في عملية فيها تنسيق بين النظام والـ Controller:

1. النظام يطلب تنفيذ عملية I/O.
2. الـ Device Controller يتعامل مع الجهاز، ويُنقل البيانات إلى الـ Local Buffer الخاص به.
3. تُنقل البيانات بين الـ Buffer والـ Main Memory وفق آلية الجهاز والنظام.
4. عند اكتمال العملية، يستطيع الـ Controller إبلاغ الـ CPU باستخدام **Interrupt**.

> ✅ النقطة المهمة: الـ **CPU وأجهزة الـ I/O ممكن ينفذوا عمليات Concurrently**؛ يعني نشاط الجهاز مش لازم يوقف كل نشاط المعالج طوال الوقت.
> كمان، الـ Controllers والمعالج قد **يتنافسون على الوصول إلى الذاكرة المشتركة**؛ وده جزء من تنظيم النظام، مش مجرد تفاصيل فيزيائية منفصلة.

## 4. Interrupts — إزاي الجهاز يلفت انتباه المعالج؟

بدل ما يفضل الـ CPU يسأل الجهاز باستمرار: «خلصت؟ خلصت؟ خلصت؟»، ممكن الجهاز يرسل **Interrupt** عند حدوث شيء يحتاج انتباه المعالج.

### آلية الـ Interrupt

لما يحصل Interrupt:

1. ينتقل التحكم إلى **Interrupt Service Routine (ISR)**، وهي الروتين المسؤول عن معالجة نوع المقاطعة.
2. يمكن استخدام **Interrupt Vector** للوصول إلى عنوان الـ Service Routine المناسبة؛ وهو هيكل يحتوي على عناوين روتينات معالجة المقاطعات.
3. لازم المعمارية تحفظ **عنوان التعليمة** التي توقّف التنفيذ عندها، حتى يمكن استكمال التنفيذ لاحقًا حسب الحالة.

الكتاب يؤكد أن الـ **Operating System نظام Interrupt-driven**: كثير من أحداثه مرتبطة بالمقاطعات التي تستدعي معالجة مناسبة، بدل الاعتماد على تنفيذ خطّي مستمر فقط.

### Interrupt vs Trap / Exception

التمييز هنا مهم:

| المصطلح | المعنى |
|---|---|
| **Interrupt** | غالبًا حدث خارجي عن التنفيذ الحالي، مثل إشارة من جهاز I/O أو مؤقّت |
| **Exception** | حدث مرتبط بتنفيذ التعليمة الحالية، مثل خطأ أثناء التنفيذ |
| **Trap** | في عرض الكتاب، مقاطعة مولّدة برمجيًا بسبب خطأ أو طلب من المستخدم؛ ويُستخدم في كثير من السياقات للإشارة إلى انتقال متعمد أو حدث استثنائي داخل التنفيذ |

> ⚠️ الـ **Trap** والـ **Exception** مش نفس معنى الـ **Hardware Interrupt** الخارجي، حتى لو كلها قد تؤدي إلى انتقال التحكم إلى النظام.

**ليه لازم نحفظ عنوان التعليمة؟**

تخيّل إن برنامجًا كان ينفّذ تعليمات، ثم وصل Interrupt من لوحة المفاتيح. النظام يعالج الحدث، وبعدها يحتاج يعرف من أين يستأنف التنفيذ. حفظ عنوان التعليمة جزء من الحفاظ على حالة التنفيذ.

### Synchronous vs Asynchronous I/O

- **Synchronous I/O:** العملية التي بدأها البرنامج تنتظر اكتمال عملية الـ I/O قبل أن يواصل الجزء المعني من التنفيذ.
- **Asynchronous I/O:** يمكن للبرنامج متابعة عمل آخر بينما عملية الـ I/O ما زالت جارية، ثم يُبلّغ باكتمالها بالطريقة التي يدعمها النظام.

في حالة الانتظار، يمكن أن يوقف النظام البرنامج أو يجعله ينتظر بطريقة معينة، أو يستخدم أسلوبًا من نوع **Busy Waiting** حيث يكرر فحص حالة الجهاز. الكتاب يذكر أيضًا انتظارًا قائمًا على تعليمة **Wait** وجدولًا لحالة الأجهزة (**Device-status table**) لمتابعة معلومات الـ I/O.

> ✅ **الفرق العملي:** Busy Waiting قد يستهلك وقت CPU في الفحص المتكرر، بينما آلية تعتمد على المقاطعات تتيح للمعالج تنفيذ عمل آخر إلى أن يصبح الحدث جاهزًا.

## 5. Storage Hierarchy — ليه عندنا أكتر من نوع ذاكرة؟

مش كل أنواع التخزين بتقدّم نفس السرعة أو السعة أو التكلفة. عشان كده الكمبيوتر بيستخدم **Storage Hierarchy**: مستويات مختلفة من التخزين، كل مستوى له خصائصه.

| المستوى | الفكرة الأساسية |
|---|---|
| **Registers** | صغيرة جدًا وسريعة جدًا، داخل المعالج |
| **Cache** | تحتفظ ببيانات وتعليمات يُتوقع استخدامها قريبًا |
| **Main Memory (RAM)** | تحتوي على البرامج والبيانات المستخدمة حاليًا |
| **Secondary Storage** | مثل SSD وHDD، لسعة أكبر واحتفاظ أطول بالبيانات |
| **Tertiary Storage** | مثل الأشرطة المغناطيسية وبعض وسائط التخزين الضوئية، غالبًا للأرشفة |

> 📌 عمومًا، كلما اقتربنا من المعالج، **تقل السعة وتزيد السرعة والتكلفة** لكل وحدة تخزين. أما المستويات الأبعد فتوفّر سعات أكبر وتكلفة أقل لكل وحدة، لكنها أبطأ.

### Bits, Bytes, Words

- **Bit:** أصغر وحدة بيانات، قيمتها 0 أو 1.
- **Byte:** يساوي 8 bits.
- **Word:** حجم بيانات طبيعي للمعالج، ويتحدد وفق المعمارية؛ **مش شرط يكون 4 أو 8 bytes في كل جهاز**.

وبالنسبة لوحدات السعة، لازم تنتبه للسياق. في الاستخدام الثنائي التقليدي:

- 1 KiB = 1024 bytes
- 1 MiB = 1024 KiB
- 1 GiB = 1024 MiB

أما وحدات SI العشرية مثل KB وMB وGB فتستخدم مضاعفات 1000. لذلك **لازم تميّز بين الاصطلاح المستخدم في السؤال**.

### RAM vs Secondary Storage

- **RAM** هي الذاكرة الرئيسية التي يحتاجها البرنامج أثناء التنفيذ، وهي عادةً **Volatile**؛ أي تفقد محتواها عند انقطاع الطاقة.
- أما **SSD أو HDD** فيحتفظان بالبيانات بعد إغلاق الجهاز، ولذلك يُستخدمان في **Secondary Storage**.

في القرص الصلب التقليدي HDD، من المصطلحات المهمة:

| المصطلح | المعنى |
|---|---|
| **Track** | مسار دائري على سطح القرص |
| **Sector** | جزء من المسار يُستخدم كوحدة لتنظيم التخزين |
| **Device Controller** | يتعامل مع عمليات الجهاز |
| **Device Driver** | برنامج في النظام يوفّر واجهة للتعامل مع الجهاز والتحكم فيه |

> ⚠️ **الـ Driver والـ Controller مختلفان:** الأول Software، والثاني مكوّن مسؤول عن التحكم في الجهاز.

### Caching — ليه بننسخ البيانات بين المستويات؟

**Caching** يعني الاحتفاظ بنسخة من البيانات في مستوى أسرع، لتقليل وقت الوصول إليها عند الحاجة مرة أخرى.

- لو المعالج احتاج بيانات موجودة في الـ Cache → **Cache Hit**.
- لو لم يجدها → **Cache Miss**، وقد يحتاج لجلبها من مستوى أبطأ.

فعالية الـ Cache لا تعتمد على وجودها فقط، بل على عوامل مثل:

- حجمها (**Cache Size**).
- البيانات التي تُحتفظ بها.
- طريقة استبدال البيانات عندما تمتلئ (**Replacement Policy**).

الـ Cache مفيدة لأن البرامج غالبًا تعيد استخدام بيانات أو تعليمات، لكن الاحتفاظ بنسخ متعددة يخلق تحديًا: لازم النظام يحافظ على صحة البيانات واتساقها.

### Data Migration وCache Coherency

قد تنتقل البيانات من Disk → RAM → Cache → Registers. بعض عمليات النقل تتم تلقائيًا ضمن عمل المعالج والنظام، وبعضها يكون تحت إدارة البرمجيات.

المشكلة تظهر عندما توجد نسخ متعددة من نفس البيانات. لو اتعدّلت نسخة وبقيت نسخة أخرى قديمة، ممكن برنامج يقرأ قيمة غير صحيحة.

- **Cache Coherency:** ضمان اتساق نسخ البيانات في الـ Caches بين المعالجات.
- في **Multitasking**، يجب أن يتعامل النظام مع أحدث قيمة للبيانات.
- في **الأنظمة الموزعة (Distributed Systems)**، المشكلة أصعب لأن نسخ البيانات قد توجد على أجهزة متعددة.

> ✅ دي نقطة مهمة في الملف: الموضوع مش مجرد سرعة التخزين، لكن كمان **صحة البيانات** عند وجود أكثر من نسخة.

## 6. Computer-System Architecture — معالج واحد ولا أكتر؟

### Single-Processor System

نظام يعتمد على معالج عام واحد (**General-purpose processor**) لتنفيذ التعليمات الأساسية، مع احتمال وجود معالجات متخصصة لبعض المهام.

### Multiprocessor Systems

تُسمى أيضًا **Parallel Systems** أو **Tightly-coupled Systems**. فيها أكثر من Processor يعملون ضمن نظام مترابط، وغالبًا يتشاركون الذاكرة والموارد.

المحاضرة تحدد ثلاث فوائد رئيسية:

1. **Increased Throughput:** إنجاز عمل أكبر خلال فترة زمنية معينة.
2. **Economy of Scale:** مشاركة الموارد قد تكون أقل تكلفة من بناء أنظمة مستقلة لكل مهمة.
3. **Increased Reliability:** إمكانية استمرار الخدمة أو تقليل أثر تعطل أحد المكونات.

ومن مفاهيم الاعتمادية:

- **Graceful Degradation:** أداء النظام قد ينخفض تدريجيًا بدلًا من توقفه بالكامل.
- **Fault Tolerance:** قدرة النظام على الاستمرار في تقديم الخدمة رغم بعض الأعطال.

### AMP vs SMP

| | **Asymmetric Multiprocessing (AMP)** | **Symmetric Multiprocessing (SMP)** |
|---|---|---|
| الفكرة | كل معالج يُسند إليه دور أو مهمة محددة؛ المعالجات ليست متساوية في مسؤولياتها | المعالجات تشارك في تنفيذ مهام النظام، ويمكن لكل معالج تنفيذ أعمال النظام المعتادة وفق تنظيمه |

> ✅ الفكرة الأساسية: **AMP** يعتمد على توزيع أدوار غير متماثل، بينما **SMP** يسمح للمعالجات بالمشاركة بصورة متماثلة في تنفيذ المهام.

### Multicore

في **Multicore Design**، يحتوي الـ Chip الواحد على أكثر من Core. وده يختلف عن وجود عدة شرائح معالجة منفصلة؛ لأننا هنا نتكلم عن عدد الـ Cores داخل شريحة المعالج.

> ⚠️ لا تخلط بين المصطلحين:
> - **CPU / Processor:** قد يُستخدمان للإشارة إلى وحدة المعالجة، بحسب السياق.
> - **Core:** وحدة معالجة داخل الشريحة؛ وقد يحتوي الـ Processor الواحد على عدة Cores.

### Clustered Systems

الـ **Cluster** مختلف عن مجرد وجود عدة Cores أو عدة Processors داخل جهاز واحد. هنا لدينا **عدة أنظمة كمبيوتر تعمل معًا**، وغالبًا تشارك التخزين عبر **Storage Area Network (SAN)**.

تُستخدم الـ Clusters لتحقيق **High Availability**؛ أي الحفاظ على الخدمة عند تعطل أحد الأنظمة.

| النوع | الفكرة |
|---|---|
| **Asymmetric Clustering** | جهاز يعمل، وآخر في وضع **Hot Standby** مستعد لتولي العمل عند الحاجة |
| **Symmetric Clustering** | عدة Nodes تشغّل تطبيقات وتراقب بعضها بعضًا |
| **High-Performance Computing (HPC)** | بعض الـ Clusters تُستخدم لإنجاز حسابات كبيرة بالتوازي، لكن التطبيق يحتاج أن يكون مكتوبًا ليستفيد من Parallelization |

> ✅ **الفرق اللي لازم يثبت:** Multiprocessing يتكلم عن معالجات داخل نظام مترابط؛ أما Clustering فيتكلم عن أنظمة متعددة تعمل معًا.

## 7. Multiprogramming vs Time-Sharing

من أهم أفكار الفصل الأول؛ لأنها تشرح لماذا لا يكفي تشغيل برنامج واحد ثم الانتظار حتى ينتهي.

### Multiprogramming

في نظام Multiprogramming، يحتفظ النظام بمجموعة من الـ **Jobs** في الذاكرة، ويختار واحدة للتنفيذ.

**ليه؟** لأن برنامجًا قد يتوقف مؤقتًا منتظرًا I/O. لو المعالج انتظر البرنامج ده، هيضيع وقتًا يمكن استغلاله في تنفيذ Job أخرى.

لذلك عندما تنتظر الـ Job الحالية، يستطيع الـ OS تحويل المعالج إلى Job أخرى جاهزة.

المصطلحات المرتبطة:

- **Job:** وحدة عمل في سياق المعالجة، والكتاب يصف Jobs بأنها Code and Data.
- **Job Scheduling:** اختيار Job من مجموعة الأعمال المتاحة للتنفيذ.
- **CPU Scheduling:** اختيار العملية التي ستحصل على المعالج من بين العمليات الجاهزة.

### Time-Sharing / Multitasking

الـ **Time-Sharing** هو امتداد منطقي للـ Multiprogramming. النظام يبدّل بين الأعمال بسرعة كافية ليتيح للمستخدم التفاعل مع البرامج أثناء عملها.

> 💡 مثلًا، أنت تكتب كودًا في VS Code، وتسمع صوتًا، والمتصفح مفتوح. مش معنى ده أن كل برنامج عنده CPU مستقل؛ النظام ينظّم التنفيذ والتبديل بين العمليات.

المحاضرة تذكر أن **Response Time** في الأنظمة التفاعلية ينبغي أن يكون **أقل من ثانية** وفق الهدف المعروض فيها.

كل مستخدم قد يكون لديه برنامج واحد أو أكثر في الذاكرة قيد التنفيذ، والبرنامج الجاري تنفيذه يُمثّل بواسطة **Process**.

### Program vs Process

| المصطلح | المعنى |
|---|---|
| **Program** | مجموعة تعليمات محفوظة، مثل ملف executable على القرص |
| **Process** | برنامج أثناء التنفيذ، مع حالته وموارده وسياق تشغيله |

> ✅ البرنامج ممكن يكون موجودًا على القرص من غير ما يكون قيد التنفيذ. لما يبدأ تشغيله، ينشئ النظام Process لإدارته.

### Swapping vs Virtual Memory

المحاضرة تذكر حالتين مهمتين:

- **Swapping:** نقل Process أو محتواها المرتبط من الذاكرة إلى التخزين، ثم إعادتها لاحقًا، لإتاحة مساحة لأعمال أخرى. تفاصيل التنفيذ تختلف حسب النظام.
- **Virtual Memory:** تتيح تنفيذ Processes لا يلزم أن تكون كل تعليماتها وبياناتها موجودة في الـ Main Memory في نفس اللحظة.

> ⚠️ **Virtual Memory مش مجرد اسم آخر للـ Swapping.** هما مفهومان مرتبطان بإدارة الذاكرة، لكنهما مش مترادفين.

## 8. Operating-System Operations — حماية النظام من البرامج

الـ OS يحتاج وسيلة تمنع البرامج العادية من تنفيذ كل ما تريده على الـ Hardware.

### Dual-Mode Operation

تدعم الأجهزة وضعين أساسيين في شرح الكتاب:

| الوضع | الوصف |
|---|---|
| **User Mode** | تنفيذ كود التطبيقات بصلاحيات محدودة |
| **Kernel Mode** | تنفيذ كود النظام بصلاحيات أوسع |

تستخدم المعمارية **Mode Bit** للتمييز بين الوضعين.

بعض التعليمات تُسمى **Privileged Instructions**؛ لا يُسمح بتنفيذها إلا في Kernel Mode. ده يمنع البرنامج العادي من تنفيذ عمليات حساسة مباشرةً، مثل بعض عمليات التحكم في الـ Hardware.

### System Call وعلاقتها بالـ Modes

لما برنامج يحتاج خدمة نظام، مثل قراءة ملف، يستخدم **System Call**. ينتقل التنفيذ إلى مسار داخل النظام بصلاحيات Kernel Mode، ثم يعود البرنامج إلى User Mode بعد انتهاء الخدمة.

> ✅ الفكرة مش إن البرنامج يتحول بالكامل إلى Kernel؛ بل إن **التحكم ينتقل إلى النظام** لتنفيذ الخدمة المطلوبة.

### Timer — منع البرنامج من احتكار الـ CPU

تخيّل برنامجًا دخل في Infinite Loop ولم يتوقف من تلقاء نفسه. كيف يستعيد النظام السيطرة؟

المحاضرة تشرح استخدام **Timer**:

1. النظام يضبط مؤقّتًا بقيمة محددة، باستخدام تعليمة ذات صلاحيات مناسبة.
2. عدّاد يتناقص وفق الساعة الفيزيائية.
3. عندما يصل إلى الصفر، يحدث Interrupt.
4. يستعيد النظام التحكم، ويستطيع متابعة جدولة العمليات أو التعامل مع البرنامج الذي تجاوز الوقت المخصص له.

> ✅ إذًا، الـ Timer آلية أساسية **لمنع برنامج من احتكار المعالج** إلى أجل غير محدد.

## 9. مسؤوليات نظام التشغيل الأساسية

دي مش مجرد قائمة للحفظ؛ كل مسؤولية منها بتحل مشكلة مختلفة في إدارة الجهاز.

### 1) Process Management

الـ OS مسؤول عن:

- Creating and deleting عمليات المستخدم والنظام.
- Suspending and resuming العمليات.
- توفير آليات **Process Synchronization** لتنظيم وصول العمليات المتزامنة إلى الموارد المشتركة.
- توفير آليات **Process Communication** لتبادل البيانات بين العمليات.
- التعامل مع **Deadlocks**، وهي حالات تنتظر فيها عمليات موارد بطريقة قد تمنعها من التقدم.

### 2) Memory Management

لازم تكون التعليمات والبيانات المطلوبة موجودة في الذاكرة لكي تُنفّذ. وليس من الضروري دائمًا وجود البرنامج بالكامل في الذاكرة في الوقت نفسه، خصوصًا مع تقنيات مثل Virtual Memory.

مسؤوليات الـ Memory Management:

1. تتبّع أجزاء الذاكرة المستخدمة ومَن يستخدمها.
2. تحديد العمليات أو الأجزاء والبيانات التي تُنقل إلى الذاكرة أو خارجها.
3. تخصيص الذاكرة (**Allocation**) وتحريرها (**Deallocation**) عند الحاجة.

والهدف هو إدارة الذاكرة بطريقة تساعد على تحسين استخدام الـ CPU والاستجابة للمستخدم.

### 3) Storage Management وFile-System Management

الـ OS يقدم **طريقة منطقية موحّدة** للتعامل مع المعلومات، بصرف النظر عن تفاصيل وسيط التخزين الفعلي. الوحدة المنطقية الأساسية التي يركز عليها الملف هنا هي **File**.

خصائص وسائط التخزين قد تختلف من حيث:

- **Access Speed**
- **Capacity**
- **Data-Transfer Rate**
- **Access Method:** مثل الوصول التسلسلي أو العشوائي.

أما File-System Management فيشمل:

- إنشاء الملفات والمجلدات وحذفها.
- توفير عمليات التعامل مع الملفات والمجلدات.
- تنظيم الوصول إلى الملفات والتحكم في الصلاحيات (**Access Control**).
- ربط الملفات بمواقع التخزين الثانوي.
- نسخ الملفات احتياطيًا إلى وسائط مستقرة وغير متطايرة (**Non-volatile Storage**).

### 4) Mass-Storage Management

التخزين كبير السعة مهم للبيانات التي لا تتسع لها الذاكرة الرئيسية، أو التي نحتاج للاحتفاظ بها مدة طويلة.

من مسؤوليات النظام:

- **Free-space Management:** تتبّع المساحة المتاحة.
- **Storage Allocation:** تحديد كيفية تخصيص مساحة للبيانات.
- **Disk Scheduling:** تنظيم طلبات الوصول إلى القرص.

ويذكر الملف أيضًا **Tertiary Storage** مثل Optical Storage وMagnetic Tape، وأن بعض الوسائط قد تكون:

- **WORM:** Write Once, Read Many Times.
- **RW:** Read-Write.

> 📌 مش كل التخزين لازم يكون سريعًا؛ أحيانًا يكون الهدف الأساسي هو **الأرشفة أو الاحتفاظ بالبيانات**.

## 10. Protection and Security

في الفصل الأول، الحماية والأمان مش مجرد كلمة واحدة.

| المصطلح | المعنى |
|---|---|
| **Protection** | التحكم في **كيفية وصول** العمليات والمستخدمين إلى موارد النظام؛ مين مسموح له يعمل إيه؟ |
| **Security** | حماية النظام من **التهديدات** ومحاولات الوصول غير المصرح به، مع الاهتمام بآليات مثل التحقق من الهوية (**Authentication**) |

> 💡 مثلًا، وجود حساب مستخدم عادي وحساب Administrator يرتبط بالصلاحيات. لكن **إثبات هوية** الشخص الذي يسجّل الدخول **مختلف** عن تحديد **الصلاحيات** التي يحصل عليها بعد الدخول.

الكتاب يضع Protection and Security ضمن الموضوعات الأساسية لفهم نظام التشغيل، إلى جانب إدارة العمليات والذاكرة والتخزين.

# Chapter 2 — System Structures

الفصل الثاني يجاوب عن سؤال مختلف: بعد ما عرفنا وظيفة الـ OS، **إزاي البرامج تتواصل معاه؟ وإزاي نصمّم النظام ونقسّمه داخليًا؟**

---

## 1. Operating System Services

الـ OS يقدم خدمات للبرامج والمستخدمين والأنظمة الأخرى. المحاضرة تحدد **ثماني خدمات رئيسية**:

| # | الخدمة | الوصف |
|---|---|---|
| 1 | **Program Execution** | تحميل البرنامج، تشغيله، وإنهاء تنفيذه. النظام مسؤول عن توفير البيئة اللازمة للتنفيذ والتعامل مع إنهائه |
| 2 | **I/O Operations** | نقل البيانات من أجهزة الإدخال والإخراج وإليها، مثل قراءة بيانات من ملف أو إرسال بيانات إلى جهاز |
| 3 | **File-System Manipulation** | قراءة الملفات وكتابتها وحذفها والبحث عنها، والتعامل مع المجلدات |
| 4 | **Communications** | تبادل المعلومات بين العمليات، بما في ذلك التواصل بين أجهزة مختلفة عبر الشبكة |
| 5 | **Error Detection** | اكتشاف الأخطاء التي قد تحدث في المعالج أو الذاكرة أو أجهزة I/O أو أثناء تنفيذ البرامج، واتخاذ الإجراء المناسب للتعامل معها |
| 6 | **Resource Allocation** | توزيع الموارد مثل CPU والذاكرة وأجهزة I/O عندما تعمل عدة Jobs أو Processes بالتزامن |
| 7 | **Accounting** | تتبّع الموارد التي يستخدمها المستخدمون أو العمليات؛ مثل مقدار الاستخدام الذي يمكن قياسه وتسجيله |
| 8 | **Protection and Security** | التحكم في الوصول إلى الموارد، والتحقق من الهوية، ومنع الوصول غير المصرح به |

> ✅ **التمييز المهم:** الـ **Services** هي ما يقدّمه النظام. أما **System Calls** فهي إحدى الطرق البرمجية التي تُستخدم لطلب خدمات من النظام.

## 2. User Operating System Interface

المستخدم يحتاج وسيلة يتعامل بها مع النظام. من أمثلتها:

- **CLI — Command-Line Interface:** التعامل عبر كتابة الأوامر.
- **GUI — Graphical User Interface:** التعامل عبر النوافذ والأيقونات والقوائم.
- **Touch Interface:** التعامل باللمس، كما في الهواتف والأجهزة اللوحية.

> ⚠️ الواجهة هنا تختلف عن الـ **System Call Interface**. الـ CLI أو GUI موجّهة أساسًا لتفاعل **المستخدم** مع النظام، بينما الـ System Call Interface تسمح لـ**البرامج** بطلب خدمات الـ Kernel.

> 💡 مثلًا، لما تكتب أمرًا في Terminal، الـ **Shell** يفسّر الأمر ويشغّل البرنامج المناسب. البرنامج بدوره قد يستدعي خدمات النظام. إذًا، الأمر الذي تكتبه **ليس بالضرورة System Call مباشرة**.

---

## 3. System Calls — إزاي البرنامج يطلب خدمة من الـ OS؟

الـ **System Call** هي واجهة برمجية للوصول إلى خدمات يوفّرها نظام التشغيل. المحاضرة تشير إلى أن هذه الواجهة تُستخدم عادةً من خلال لغات عالية المستوى مثل C وC++، وأن البرامج غالبًا تصل إليها عن طريق **API** بدل استدعاء تفاصيل النظام مباشرة.

### API vs System Call

**API — Application Programming Interface** هي مجموعة من الوظائف المتاحة للمبرمج، مع تحديد الـ Parameters التي تستقبلها والـ Return Values المتوقعة.

المحاضرة تذكر ثلاثة أمثلة مشهورة:

- **Win32 API:** لأنظمة Windows.
- **POSIX API:** للأنظمة المتوافقة مع POSIX، مثل UNIX وLinux وmacOS.
- **Java API:** لبرامج Java التي تعمل ضمن بيئة JVM.

| المصطلح | معناه |
|---|---|
| **API** | واجهة برمجية يستخدمها البرنامج أو المبرمج |
| **System Call** | طلب خدمة من نظام التشغيل عبر آلية النظام |
| **System Call Interface** | الجزء الذي يربط طلبات System Calls بتنفيذها داخل الـ Kernel |

> ✅ الـ API قد تكون أسهل للمبرمج، وتخفي عنه تفاصيل تنفيذ الخدمة على مستوى النظام.

### مثال: printf() وwrite()

افترض إن عندك برنامج C:

```c
#include <stdio.h>

int main(void) {
    printf("Hello OS
");
    return 0;
}
```

أنت كتبت `printf()`، وهي دالة من مكتبة C القياسية. في المثال التعليمي بالكتاب، تُستخدم `printf()` لتوضيح كيف يمكن لدالة مكتبية أن تؤدي في النهاية إلى استدعاء `write()` لطلب الكتابة من نظام التشغيل.

> ⚠️ **انتبه:** مش كل استدعاء لـ `printf()` يؤدي فورًا إلى System Call. المكتبة قد تستخدم Buffer لتجميع البيانات، ثم تنفذ الكتابة الفعلية لاحقًا، حسب إعدادات الـ Buffering وطريقة الاستخدام.

**الرحلة المفاهيمية:**

```text
C Program              →  printf("Hello OS
")
C Standard Library     →  تنسيق النص وإدارة الـ Buffer عند الحاجة
System Call Interface  →  مثل طلب write() عند تنفيذ الكتابة الفعلية
OS Kernel              →  ينفّذ خدمة الكتابة ويرجع النتيجة
```

> ✅ **الفكرة الأساسية:** المبرمج لا يحتاج معرفة التفاصيل الداخلية لكل نظام تشغيل حتى يستخدم الوظائف المتاحة في الـ API. لكنه يحتاج معرفة سلوك الوظيفة والـ Parameters والـ Return Values المتوقعة.

## 4. System Call Implementation

كيف يعرف النظام أي خدمة يجب تنفيذها عندما يستقبل System Call؟

بحسب شرح المحاضرة، لكل System Call عادةً **Number** مرتبط بها. وتحتفظ الـ **System-Call Interface** بجدول (**Table**) يُستخدم للوصول إلى الخدمة المناسبة وفق هذا الرقم.

**التسلسل العام:**

1. البرنامج يطلب خدمة من خلال الواجهة المناسبة.
2. يصل الطلب إلى System Call Interface.
3. تُحدّد الخدمة المطلوبة باستخدام رقمها.
4. يتم استدعاء الـ System Call المناسبة داخل الـ Kernel.
5. ترجع النتيجة: Status و/أو Return Value بحسب الخدمة.

المبرمج عادةً لا يحتاج معرفة كيفية تنفيذ الخدمة داخليًا؛ يحتاج فقط فهم الـ API وما الذي ستفعله الخدمة المطلوبة.

وتشير المحاضرة إلى دور **Run-time Support Library**، وهي مجموعة وظائف مكتبية مرتبطة ببيئة التشغيل والمترجم، تساعد على إخفاء كثير من تفاصيل التعامل مع النظام.

---

## 5. Passing Parameters to System Calls

استدعاء الخدمة وحده لا يكفي؛ النظام يحتاج يعرف تفاصيل الطلب. مثلًا، لو طلبت قراءة ملف، فهناك معلومات مرتبطة بالملف والبيانات المطلوب التعامل معها.

المحاضرة تشرح ثلاث طرق عامة لتمرير الـ Parameters:

| الطريقة | الوصف |
|---|---|
| **Method 1 — Registers** | تمرير الـ Parameters داخل Registers المعالج. دي طريقة بسيطة وسريعة، لكن عدد الـ Registers محدود؛ لذلك قد لا تكفي لكل الـ Parameters |
| **Method 2 — Memory Block / Table** | وضع الـ Parameters في Block أو Table داخل الذاكرة، ثم تمرير **عنوان الـ Block** في Register. المحاضرة تذكر أن هذا الأسلوب مستخدم في **Linux وSolaris** |
| **Method 3 — Stack** | يضع البرنامج الـ Parameters على الـ Stack، أي يعمل لها Push، ثم يقرأها النظام بالطريقة المناسبة ويزيلها باستخدام Pop |

> 📌 الكتاب يشير إلى أن طريقتي الـ **Block** والـ **Stack** لا تفرضان نفس القيود المرتبطة بعدد الـ Registers على عدد أو طول الـ Parameters.

> ✅ **الفرق الذي ينبغي فهمه:** هذه طرق **لنقل بيانات الطلب** إلى النظام، وليست أنواعًا مختلفة من خدمات الـ System Calls.

---

## 6. Types of System Calls

الـ System Calls تُصنّف حسب نوع الوظيفة التي تقدمها. افهم كل فئة من خلال المشكلة التي تحلها.

### A. Process Control

عمليات تتعلق بإدارة تنفيذ البرامج والعمليات، مثل إنشاء عملية أو إنهائها، وتحميل برنامج وتشغيله، والتحكم في تنفيذ العملية وانتظار انتهائها عند الحاجة.

> 💡 مثال مفاهيمي: برنامج يريد تشغيل برنامج آخر؛ يحتاج آلية تسمح بإنشاء التنفيذ الجديد والتعامل مع نتيجته.

### B. File Management

عمليات تتعلق بالملفات، مثل إنشاء ملف أو حذفه، وفتحه وإغلاقه، والقراءة والكتابة، والحصول على معلوماته أو تغيير بعض خصائصه.

> 💡 مثلًا، فتح ملف ثم قراءة محتواه يختلف عن إنشاء Process؛ الأولى عملية File Management، والثانية Process Control.

### C. Device Management

التعامل مع أجهزة I/O، مثل طلب الوصول إلى جهاز، أو القراءة منه والكتابة إليه، أو الحصول على معلومات تخصه، بحسب ما يسمح به النظام.

### D. Information Maintenance

الحصول على معلومات النظام أو العملية أو الوقت والتاريخ، أو التعامل مع بعض الخصائص التي يحتفظ بها النظام.

### E. Communications

تبادل البيانات بين Processes، وقد يشمل إنشاء قنوات اتصال، وإرسال الرسائل واستقبالها، أو استخدام وسائل تواصل بين الأنظمة.

### F. Protection

التحكم في الصلاحيات والوصول إلى الموارد، بحيث لا تتمكن عملية من الوصول إلى مورد لا تملك صلاحية استخدامه.

> ⚠️ خلي بالك إن التصنيفات دي بتوصف **نوع الخدمة المطلوبة**، وليست أسماء لواجهات مستخدم أو أنواع من لغات البرمجة.

---

## 7. System Programs

الـ **System Programs** تختلف عن الـ **System Calls**:

- الـ **System Calls** هي **الآلية** التي يطلب بها البرنامج خدمات النظام.
- الـ **System Programs** هي **برامج مساعدة** توفّر بيئة عملية ومريحة لاستخدام النظام وتطوير البرامج.

أمثلة على أدوارها:

| الدور | الوصف |
|---|---|
| **File Management** | أدوات إنشاء الملفات ونسخها وحذفها وعرض محتواها |
| **Status Information** | عرض معلومات مثل الوقت، والمساحة المتاحة، ومعلومات النظام |
| **File Modification** | أدوات تعديل الملفات ومحتوياتها |
| **Programming-Language Support** | مثل Compilers وAssemblers وDebuggers |
| **Program Loading and Execution** | أدوات تساعد على تحميل البرامج وتشغيلها |
| **Communications** | أدوات للتواصل وتبادل المعلومات |
| **Background Services** | خدمات تعمل في الخلفية لتوفير وظائف للنظام |

> 💡 مثلًا، الـ **Compiler** يحوّل الكود إلى صيغة قابلة للتنفيذ، لكنه **ليس هو الـ Kernel**. والـ Terminal أو Shell يساعدك على تشغيل الأوامر، لكنه لا يصبح بذلك هو نظام التشغيل بالكامل.

---

## 8. Operating-System Design and Implementation

تصميم نظام تشغيل لا يقتصر على كتابة وظائف كثيرة؛ المشكلة هي **كيف نحدد المسؤوليات، وننظم مكونات النظام، ونوفّر واجهات واضحة بينها**.

من أهداف التصميم المهمة:

- جعل النظام سهل الاستخدام والتطوير.
- تحقيق أداء مناسب.
- تقليل التعقيد.
- الحفاظ على الحماية والاعتمادية.

### Policy vs Mechanism

| المصطلح | المعنى |
|---|---|
| **Policy** | ما القرار الذي يجب اتخاذه؟ |
| **Mechanism** | كيف يتم تنفيذ القرار؟ |

> 💡 مثال توضيحي: اختيار أي Process تحصل على CPU الآن هو قرار يرتبط بالـ **Policy**، أما الآليات التي تسمح بتبديل التنفيذ والتحكم في المعالج فتندرج ضمن الـ **Mechanism**.
>
> ✅ الفصل بين الاثنين مفيد لأنك قد **تغيّر سياسة الجدولة دون الحاجة إلى إعادة تصميم كل آليات تبديل العمليات**.

## 9. Operating-System Structure — كيف نُقسّم النظام من الداخل؟

دي من أهم موضوعات الفصل الثاني. بدل ما نتعامل مع الـ OS ككتلة واحدة، توجد طرق مختلفة لتنظيم مكوناته: **Simple Structure**، و**UNIX Monolithic**، و**Layered Approach**، و**Microkernel**، و**Modules**، و**Hybrid Systems**.

### A. Simple Structure — مثال MS-DOS

في النموذج البسيط الذي تعرضه المحاضرة، صُمّم **MS-DOS** لتوفير أكبر قدر من الوظائف في مساحة صغيرة.

**خصائصه:**

- لا توجد تقسيمات واضحة ومحكمة إلى Modules مستقلة.
- توجد بعض البنية، لكن واجهات المكونات ومستويات الوظائف ليست منفصلة جيدًا.
- الفصل بين مكونات النظام محدود.

| الميزة | العيوب |
|---|---|
| البساطة وسهولة التنفيذ نسبيًا | عدم تقسيم النظام بوضوح إلى Subsystems، وضعف الفصل بين المستويات، وإمكانية الوصول المباشر إلى الـ Hardware |

> ✅ المشكلة في هذا النموذج ليست أن النظام لا يحتوي أي تنظيم إطلاقًا؛ بل أن **الفصل بين مكوناته ليس قويًا** بما يكفي لتسهيل العزل والصيانة.

### B. Traditional UNIX — Monolithic Structure

الكتاب يشرح أن UNIX التقليدي يتكون من جزأين رئيسيين:

- **System Programs**
- **Kernel**

ويصف الـ Kernel بأنه الجزء الموجود **أسفل System-Call Interface** و**وفوق Physical Hardware**.

يتولى الـ Kernel وظائف كثيرة، منها:

- File System
- CPU Scheduling
- Memory Management
- وظائف أخرى لنظام التشغيل

عندما تُجمع وظائف عديدة في Kernel كبير ومترابط، يُسمّى هذا التنظيم **Monolithic Structure**.

| المزايا | العيب |
|---|---|
| أداء أعلى، مع وجود قدر من الحماية | التعقيد الكبير الذي يجعل الصيانة والتطوير أصعب |

> ✅ الفكرة: قرب المكونات من بعضها داخل الـ Kernel قد يقلل تكلفة التواصل بينها، لكنه يجعل النظام **أكثر تعقيدًا** إذا لم تكن الحدود والمسؤوليات واضحة.

### C. Layered Approach

في Layered Structure، يُقسّم نظام التشغيل إلى **Layers**، كل Layer مبنية فوق الطبقات الأدنى منها.

- **Layer 0:** الـ Hardware.
- **Layer N:** أعلى طبقة، وهي User Interface في النموذج المعروض.
- كل طبقة تستخدم وظائف وخدمات الطبقات الأدنى منها.

```text
Layer N ── User Interface
    ▲
Intermediate Layers
(كل طبقة تعتمد على خدمات الطبقات الأدنى)
    ▲
Layer 0 ── Hardware
```

| المزايا | العيوب |
|---|---|
| يمكن تطوير كل Layer واختبارها وتصحيحها بصورة مستقلة نسبيًا. وإذا ظهرت مشكلة داخل طبقة، يصبح تحديد نطاق البحث أسهل، بشرط صحة الطبقات التي تعتمد عليها | من الصعب تحديد أفضل ترتيب للطبقات وحدود مسؤولياتها. وقد تكون البنية أقل كفاءة بسبب المرور عبر طبقات متعددة عند تنفيذ بعض العمليات |

> ⚠️ الـ Layering يعتمد على **وضوح الحدود** بين الطبقات؛ لو طبقة احتاجت الوصول مباشرةً إلى وظائف طبقة أعلى منها، قد يختل التصميم.

### D. Microkernel

الفكرة الأساسية في Microkernel Structure هي **نقل أكبر قدر ممكن من وظائف النظام خارج الـ Kernel إلى User Space**، مع إبقاء النواة أصغر ما يمكن وفق التصميم.

بدل وجود وظائف كثيرة داخل Kernel واحد، يمكن تشغيل بعض الخدمات كعمليات أو Modules في User Space، وتتواصل عبر **Message Passing**.

المحاضرة تذكر **Mach** مثالًا على Microkernel، وتذكر Windows NT v1 وارتباط جزء من نواة Mac OS X المسماة **Darwin** بـ Mach.

| المزايا | العيب الأساسي |
|---|---|
| أسهل في التوسعة (Easier to Extend) | تكلفة التواصل بين User Space وKernel Space قد تؤثر في الأداء، بسبب عمليات التواصل وتبادل الرسائل والتحولات المطلوبة |
| أسهل في نقل النظام إلى معمارية جديدة (Portability) | |
| أكثر قابلية للاعتمادية؛ لأن مقدار الكود الذي يعمل بصلاحيات Kernel Mode أقل | |
| يمكن أن يوفّر حماية أفضل | |

> 📌 الملف يشير إلى أن **Windows XP** صُمّم ليكون أقرب إلى **Monolithic** من Microkernel الخالص، في سياق التعامل مع تكلفة الأداء.

### E. Modules

الأنظمة الحديثة كثيرًا ما تستخدم **Loadable Kernel Modules**. الفكرة هنا ليست وضع كل الوظائف داخل نواة واحدة ضخمة ثابتة، ولا نقل كل الخدمات خارج النواة كما في Microkernel.

بدل ذلك:

- توجد مجموعة من الخدمات الأساسية في الـ Kernel.
- كل مكوّن أساسي يكون منفصلًا نسبيًا.
- تتواصل المكونات عبر **Known Interfaces**.
- يمكن تحميل Modules عند بدء التشغيل أو أثناءه، بحسب الحاجة.
- يمكن إضافة وظائف جديدة إلى الـ Kernel عن طريق **الربط الديناميكي (Dynamic Linking)**.

الملف يصف هذا الأسلوب بأنه يشبه الـ **Layered Approach** من حيث التنظيم، لكنه أكثر مرونة.

**المزايا المذكورة:**

- Kernel صغير وفعّال نسبيًا.
- سهولة ربط الـ Modules بعضها ببعض دون الحاجة إلى Message Passing كما في نموذج Microkernel المعروض.

> 💡 مثال في المحاضرة: **Solaris**.

### F. Hybrid Systems

الأنظمة الحديثة لا تتبع دائمًا نموذجًا واحدًا خالصًا. **Hybrid System** يجمع خصائص من أكثر من بنية للوصول إلى توازن بين الأداء والحماية وسهولة الاستخدام.

المحاضرة تذكر أمثلة:

- Mac OS X
- iOS
- Android

### مقارنة تثبّت الفروق

| Structure | الفكرة الأساسية | أهم ميزة | أهم تحدٍ |
|---|---|---|---|
| **Simple** | تنظيم محدود وفصل ضعيف | البساطة | صعوبة العزل والصيانة |
| **Monolithic** | وظائف كثيرة داخل Kernel | الأداء | التعقيد |
| **Layered** | طبقات ذات اعتماد منظم | سهولة التطوير والتصحيح | ترتيب الطبقات والكفاءة |
| **Microkernel** | نقل أكبر قدر من الخدمات إلى User Space | العزل والمرونة | تكلفة التواصل |
| **Modules** | مكونات قابلة للتحميل داخل Kernel | المرونة مع أداء جيد | إدارة حدود المكونات وتوافقها |
| **Hybrid** | الجمع بين أكثر من أسلوب | موازنة الاحتياجات | تعقيد التصميم |

> ✅ **نقطة فهم مهمة:** لا يوجد نموذج مثالي لكل الظروف. الاختيار يعتمد على المفاضلة بين **Performance** و**Modularity** و**Security** و**Maintainability**.

## 10. Operating-System Debugging

الـ **Debugging** هو عملية اكتشاف الأخطاء وتحليل أسبابها وإصلاحها. وفي أنظمة التشغيل، الموضوع مهم لأن المشكلة قد تكون في تطبيق، أو في Kernel، أو في تفاعل النظام مع الـ Hardware.

من المصطلحات المرتبطة بالموضوع:

| المصطلح | المعنى |
|---|---|
| **Log Files** | سجلات تحتوي على أحداث ورسائل قد تساعد في تحديد سبب المشكلة |
| **Core Dump** | معلومات عن حالة برنامج عند انهياره، يمكن تحليلها لمعرفة ما حدث |
| **Crash** | توقف غير متوقع قد يصيب تطبيقًا أو النظام نفسه |

> ✅ الفكرة الأساسية أن اكتشاف الخطأ ليس دائمًا معناه أن الكود الذي **ظهر** عنده الخطأ هو **مصدره الحقيقي**؛ فقد تكون المشكلة بدأت في مكان آخر، ثم ظهرت آثارها لاحقًا.

الـ Debugging يساعد في تحديد مكان الخلل، وفهم الظروف التي أدت إليه، والتحقق من أن الإصلاح عالج المشكلة فعلًا.

---

## 11. System Generation (SYSGEN)

**System Generation — SYSGEN** هو إعداد نظام التشغيل ليتوافق مع تكوين جهاز كمبيوتر معين.

**ليه نحتاجه؟** لأن الأجهزة تختلف في المعالج، والذاكرة، وأجهزة الإدخال والإخراج، ومكونات التخزين. النظام يحتاج أن يكون مناسبًا للتكوين الذي سيعمل عليه.

الفكرة العامة:

1. تحديد خصائص الـ Hardware والتكوين المستهدف.
2. اختيار أو إعداد المكونات والإعدادات المناسبة.
3. تجهيز نظام التشغيل ليعمل على ذلك التكوين.

> ✅ إذًا، **SYSGEN يتعلق بتخصيص أو إعداد النظام وفق خصائص الجهاز**، وليس هو نفسه عملية تشغيل الجهاز في كل مرة.

---

## 12. System Boot

الـ **Booting** هو عملية بدء تشغيل النظام وتحميل الـ Kernel لكي يبدأ التنفيذ.

اربطه بما شرحناه في الفصل الأول: الـ **Bootstrap Program** يبدأ عند تشغيل الجهاز أو إعادة تشغيله، ويهيّئ النظام ويحمل الـ Kernel ثم يبدأ تشغيله. بعد ذلك يستكمل النظام تهيئة مكوناته وخدماته وفق تصميمه.

```text
Power On / Restart
    ▼
Bootstrap / Bootloader Stage
    ▼
Load and Start the Kernel
    ▼
Initialize System Components and Services
    ▼
System Ready for Use
```

**الفرق بين المصطلحين:**

| المصطلح | المعنى |
|---|---|
| **Bootstrap Program** | البرنامج الأولي الذي يساعد على بدء تشغيل النظام وتحميل الـ Kernel |
| **Kernel** | الجزء الأساسي الذي يتولى وظائف نظام التشغيل |
| **System Boot** | العملية الكاملة التي ينتقل بها الجهاز من حالة التشغيل الأولي إلى نظام جاهز للاستخدام |

# مراجعة تربط الفصلين ببعضهما

خلينا نربط كل ما درسناه في **سيناريو واحد**: فتحت برنامجًا على جهازك، وطلبت منه قراءة ملف ومعالجة البيانات ثم عرض النتيجة.

1. **Booting:** الجهاز يبدأ التشغيل، ويُحمّل الـ Kernel.
2. **Process Management:** النظام يدير العملية التي تمثل البرنامج أثناء التنفيذ.
3. **Memory Management:** يوفّر المساحة المطلوبة للتعليمات والبيانات ويتابع استخدامها.
4. **System Call:** البرنامج يطلب خدمة مناسبة من النظام لقراءة الملف.
5. **File-System Management:** النظام يتعامل مع الملف ومعلوماته وصلاحيات الوصول إليه.
6. **Device Controller and Interrupts:** جهاز التخزين ينفّذ عملية القراءة، ويمكنه إبلاغ المعالج باكتمال العملية عبر Interrupt.
7. **CPU Scheduling:** إذا كانت العملية تنتظر I/O، يمكن للنظام تشغيل Process أخرى جاهزة.
8. **Caching:** قد تستفيد العملية من وجود البيانات في مستوى تخزين أسرع بدل إعادة جلبها من مستوى أبطأ.
9. **Protection:** النظام يتحكم في صلاحيات الوصول إلى الذاكرة والملفات والأجهزة.
10. **System Structure:** الطريقة التي بُني بها الـ OS داخليًا تؤثر في كيفية تنظيم هذه الخدمات والتواصل بينها.

> 📌 **دي الصورة الكبيرة:** الفصل الأول يعرّفك بمكونات النظام ومسؤولياته وطريقة عمله، بينما الفصل الثاني يشرح خدماته وواجهاته وطرق تنظيمه داخليًا.

# اختبار سريع على أهم الفروق

**1. أي اختيار يصف الـ Kernel بدقة أكبر؟**

- ☐ كل البرامج التي يستخدمها الشخص على الكمبيوتر
- ☐ الجزء الأساسي من نظام التشغيل
- ☐ جهاز يتحكم في الـ SSD
- ☐ واجهة المستخدم الرسومية

**2. عندما ينتهي جهاز I/O من عملية ويبلغ المعالج، ما الآلية المرتبطة بذلك؟**

- ☐ Cache Miss
- ☐ System Generation
- ☐ Interrupt
- ☐ Layered Structure

**3. ما الفرق الأساسي بين Multiprogramming وTime-Sharing في شرح الفصل؟**

- ☐ لا يوجد فرق على الإطلاق
- ☐ Time-Sharing يتيح تفاعل المستخدم بسبب التبديل المتكرر بين الأعمال
- ☐ Multiprogramming يتطلب دائمًا عدة CPUs
- ☐ Time-Sharing لا يستخدم Processes

**4. أي أسلوب يمرر عنوان Block في الذاكرة يحتوي على الـ Parameters؟**

- ☐ Registers فقط
- ☐ Memory Block / Table
- ☐ Interrupt Vector
- ☐ Bootstrap

**5. ما أبرز عيب مرتبط بالـ Microkernel في المحاضرة؟**

- ☐ لا يدعم الحماية
- ☐ لا يمكن توسيعه
- ☐ تكلفة التواصل بين User Space وKernel Space قد تؤثر في الأداء
- ☐ يجب أن يكون كل شيء في Layer واحدة

**6. ما الفرق بين API وSystem Call؟**

- ☐ هما دائمًا نفس الشيء حرفيًا
- ☐ API واجهة برمجية، وSystem Call طلب خدمة من نظام التشغيل
- ☐ API هو Hardware وSystem Call هو RAM
- ☐ System Call برنامج رسومي
